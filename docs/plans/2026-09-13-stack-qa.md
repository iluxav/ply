# Multi-repo stack QA — web/server/db, build-on-host, small box

**Goal:** prove ply's strongest single-host claim end to end — point one
deployment order at GitHub and stand up a classic **web + server + db** stack
that spans **three separate repos**, built on a $6 droplet, wired
automatically, with per-repo redeploy.

Run 2026-09-13 on a DigitalOcean droplet against **v0.1.99 → v0.1.100**. It
passed, and surfaced (and we fixed) two real bugs — see [Findings](#findings).

## The repos (public)

- `iluxav/qa-stack` — the composition (`[package]` + three `[[service]]`): the
  topology as one recipe. The deployment order points here.
- `iluxav/qa-server` — a Node API that reaches postgres via `after`-injected
  `DB_HOST`/`DB_PORT`; its own `ply.toml` (entrypoint/port/health).
- `iluxav/qa-web` — a Node page that calls qa-server via `after`-injected
  `SERVER_HOST`/`SERVER_PORT`; no deps.

`qa-stack/ply.toml`:

```toml
[package]
name = "qa-stack"
version = "0.1.0"

[[service]]
run = "postgres@17"
name = "db"
publish = ["internal:5432"]
volume = ["qa-pgdata:/var/lib/postgresql/data"]
env = { POSTGRES_PASSWORD = "qa-secret" }   # table form works on v0.1.100+; array on 0.1.99

[[service]]
run = "git+https://github.com/iluxav/qa-server"
name = "server"
build = "npm install"
after = ["db"]
publish = ["internal:3001"]
env = { POSTGRES_PASSWORD = "qa-secret" }

[[service]]
run = "git+https://github.com/iluxav/qa-web"
name = "web"
after = ["server"]
publish = ["8080:3000"]
```

## Droplet

- DigitalOcean **1GB/1vCPU ($6)** is the reliable target; **512MB ($4)** is the
  hero test → then `sudo ply setup --swap 2G`.
- Create with your SSH key baked in: DO UI → Authentication → SSH Key, or
  `doctl compute droplet create ply-qa --image ubuntu-24-04-x64 --size s-1vcpu-1gb --ssh-keys <id> --wait`.
- `--ssh-keys` uses the key **already in your DO account**; if you pick a key
  whose local private half isn't your default identity, SSH with
  `ssh -i ~/.ssh/<key> root@<ip>` (or add a `~/.ssh/config` Host block).

## Run

```sh
curl -fsSL https://plybox.sh/install.sh | sh
sudo ply setup --edge        # Caddy + the deployments watcher + the 1-min timer
# 512MB only: sudo ply setup --swap 2G

# one line, points at GitHub — no build/entrypoint spelled out (recipes rule)
echo 'repo = "https://github.com/iluxav/qa-stack"' | sudo tee /var/lib/ply/deployments/qa.toml

watch -n2 'cat /var/lib/ply/deployments/.status/qa.status; echo; echo ---; ply ps'
```

Heredoc note: with `<<'EOF'` the closing `EOF` must be flush-left (no
indentation) or the shell hangs on `>`. The `echo | tee` above avoids it.

## Verify

- `ply ps` shows three units: `db`, `server`, `web` (boot order respects `after`)
- `curl http://<ip>:8080` → `{"service":"qa-server","db":"ok","hits":0}` —
  web→server→db across three repos, no hardcoded addresses
- `curl -X POST http://<ip>:8080` a few times → `hits` climbs (the write path)
- **per-repo redeploy:** push a one-liner to `qa-web` → within ~60s only `web`
  rebuilds; `db`/`server` uptimes untouched; `hits` survives (data tier undisturbed)
- **cleanup-on-remove:** `sudo rm /var/lib/ply/deployments/qa.toml` → all three
  stop and units vanish; `ply volume ls` shows `qa-pgdata` kept

## Findings

Running it end to end caught two real bugs (fixed in **v0.1.100**):

1. **Composition members rebuilt every reconcile beat.** The build
   short-circuit reconstructed the expected image name from the MEMBER name
   (`server`) while the pack names the image after the repo's PACKAGE
   (`qa-server`); they differ in a composition, so `<name>-<ver>.img` never
   existed and every `git+` member rebuilt each minute (respinning its builder,
   and for a real build re-running it — bad on a small box). Fix: record the
   produced image path in `.ply-build/image` and key the skip on that
   (`current_build`). Single-app deploys were unaffected (name usually equals
   the package).
2. **Member `env` only accepted `["KEY=VALUE"]`.** The first stack anyone
   writes copies a single-app manifest's `[env]` table and hit a confusing `e`
   error. Fix: accept a table too; the error now names `env` and shows both.

## The gap this validates

The multi-repo, build-on-host, per-repo-CD story on a single well-provisioned
box **works and is strong** — the thing neither a Coolify compose file (one
build context) nor Kamal (single-app-per-config) expresses as one recipe. The
monorepo-subdir case (`run = "./server"`) is deliberately rejected on a host
(`"a local path — a ply up dev thing"`) — that rejection is the spec for the
next feature: a **`docker-compose.yml` importer** (compose is monorepo-subdir),
which is ply's real weakest point (onboarding breadth), not multi-host.
