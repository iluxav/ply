# ply vs Docker under load — results, 2026-09-05

Run: `results/20260905T185722Z/` (31 cells, 41 min). Box: 12-core Ryzen 9600X laptop, 14 GiB,
kernel 7.0, ply built from the working tree at 10:59 (egress + F1–F5),
Docker 29.4.1, oha 1.16 on the same host. Docker is the reference. Full
tables: `report.md` in the run directory; spec in
`docs/superpowers/specs/2026-09-05-ply-vs-docker-bench-design.md`.

## The one-paragraph version

Where no runtime machinery sits in the request path, ply and Docker are the
same: direct-to-instance `/ping` 1.04×, writes 1.02×. Everything that goes
through ply's published-port relay pays for it in CPU — about three cores at
430k requests/s — and that CPU comes off the box's throughput, so published
paths land at 0.62–0.72× of Docker, whose port publishing is kernel DNAT and
costs nothing. The relay is not badly written: on the one path where Docker
also relays in user space (`127.0.0.1`, `docker-proxy`), ply is 1.01× the
throughput at 0.84× the CPU. It is an architecture cost, and it is paid twice
when the database also sits behind `--publish internal:`. The egress
contract costs nothing measurable. Nothing leaked over a 10-minute soak.
One real defect: a rolling restart under load dropped 131 of 25.6 M requests.

"rt CPU s" is CPU-seconds consumed by the *runtime's own processes* during
the 15 s cell (ply: the run parents; Docker: dockerd, containerd, shims,
docker-proxy). 45 s in 15 s = three cores.

Reading the table:

- **Direct ping is the control.** No relay anywhere, equal numbers. The
  kernel, namespaces, veth and bridge cost the same in both.
- **Two relays, each ~15% of read throughput.** Direct/read still has the DB
  behind `internal:5432` (26 CPU-s, 0.85×). Published/read has the API relay
  too (44 CPU-s, 0.72×). The DB-direct variant below removes the DB relay
  and recovers exactly that much.
- **Writes are Postgres-bound** (~66k/s in every cell), so the relay's CPU
  shows (17.5 s) but the throughput does not move. On a workload that is
  not CPU-starved, the relay costs cores, not requests.
- **Latency:** the relay adds ~50 µs at p50 (0.06→0.11 ms) and nothing
  visible at p99. It is a CPU tax, not a latency tax.
- **Per-request efficiency vs docker-proxy** (127.0.0.1 path): ply 45.4 s
  for 419k rps, Docker 54.0 s for 414k rps. Docker's *default* path is the
  kernel one, though; ply has no kernel path.

Relay mechanics behind the numbers: `ply-core/src/runtime/publish.rs`
spawns two threads per connection and `std::io::copy`s each direction.
Thread peak in the parents at c=64 was 211 (API relay 128 + DB pool relay
64 + base), FDs 466.

| egress audit | read | 180k | 0.98× | 44.8 | 1.01× |
| egress enforce | ping | 422k | 0.95× | 46.8 | 0.98× |
| egress enforce | read | 181k | 0.98× | 44.8 | 1.01× |

- **The egress contract is free.** Audit and enforce are within 2–6% on
  throughput and within 3% on CPU of the same workload with egress off; the
  6% on ping is inside this box's run-to-run noise (Docker's own ping cells
  vary 656k–714k). The nft sets are touched only on `ct state new`, and a
  pooled app makes few new connections.
- **Half the relay cost is the database hop.** Pointing the app at the
  instance address instead of the `internal:` port cuts runtime CPU 41–51%
  and gives back the read throughput.

## Churn

| cell | ply | docker | note |
|---|---|---|---|
| keep-alive off, c=64, 15 s | 7.2k rps, p99 12.6 ms, 13.1 CPU-s | 9.0k rps, p99 9.4 ms, 0 CPU-s | both client-bound: one host, ephemeral ports, conntrack at 64k. Ratio 0.81× and +3 ms p99 is the thread-per-connection spawn; absolute numbers mean nothing |
| scale 1→4→1 under 60 s load | 427k rps, 0 errors, 184.6 CPU-s | 618k rps (3 idle extras started/stopped), 0 errors, 1.3 CPU-s | no errors either side; ply's ratio (0.69×) is the steady-state relay tax, not the churn. Parent FDs peaked at 1164, RSS at 45 MB with four instances |
| rolling restart at scale 2 under load | 427k rps, **131 errors** ("connection closed before message completed") | — | **finding.** 0.0005% of requests, but not zero |

On the rolling restart: the bench API has no graceful shutdown — Go's
`ListenAndServe` dies on SIGTERM with requests in flight — and an L4 relay
cannot see request boundaries, so it cannot drain a keep-alive connection
on the app's behalf. Two things are true at once: a well-behaved app would
have finished those 131 requests, and ply's roll does not currently give it
a drain window (stop routing new connections to the retiring slot, then
wait) before the signal. Re-test after adding `http.Server.Shutdown` to the
bench API; if errors remain, the drain step is ply's to add.

## What to do with this

1. **A kernel path for `--publish`.** nftables DNAT in the host namespace —
   `numgen inc mod N` over a map the parent rewrites when the pool changes —
   keeps the parent as the single owner of pool truth and removes ~3 cores
   per 430k rps and the thread-per-connection model. Rootless keeps the
   relay (no netfilter there), the same split egress already made.
   `splice(2)` in the relay is the incremental alternative and halves the
   copies, not the threads.
2. **The same for `internal:`,** or steer database wiring to the instance
   address (`<name>.ply`) in docs — with the caveat that the relay is what
   gives a dependency a stable address across rolls.
3. **Drain before SIGTERM in rolls,** and re-run the rolling-restart cell
   with a graceful bench API to separate ply's share from the app's.
4. **Harness debts.** `app_rss_kb` for ply samples the instance's init
   process, not the app; the keep-alive-off cell needs a second host or a
   widened ephemeral range to mean anything in absolute terms.

## Caveats

One laptop, one run per cell, load generator sharing the 12 cores with
both runtimes — which is exactly why the relay's CPU turns into lost
throughput here; on a server where the app is the bottleneck it would
show as cores, not requests. Docker's Postgres is the official image, ply's
is the Debian keg, both 17.x. Thermal and clock drift over 41 minutes:
Docker's own identical ping cells span 656k–714k, so ratios inside
0.9–1.1 are noise.

(`ply-core/src/runtime/ns/kpublish.rs`); the relay stays for rootless, macOS
and `127.0.0.1`. Same box, same binary, four hours later.

| soak 10 min at 50k rps | flat, 470 CPU-s | flat, **0.1 CPU-s**, RSS 22 MB flat | flat, 0.2 CPU-s | |

Every published-path cell is now at or above Docker's, with the runtime's
CPU at zero — the cost was the architecture, and it is gone. The
`internal:` database hop no longer costs anything either, so the DB-direct
variant stopped mattering. Egress still costs nothing on top.

**Rolling restart, still 128 errors — two causes, one fixed after this run.**
The roll's errors split into 57 "connection error" and 71 "connection closed
before message completed". The 57: every launch path except the roll put a
new instance into the pool the moment it was spawned; the relay hid that by
retrying the next backend on a refused connect, the kernel cannot. Fixed
after this run: an instance joins its pool only once its first published
port accepts (`publish::Membership`, checked every loop turn; the roll joins
right after the health gate). The 71: the retiring instance closing
keep-alive connections that the client is about to reuse — the app's side
of a clean roll. The bench API now turns keep-alive off before `Shutdown`
so clients reconnect to the surviving instance (`docs/deploy.md`, "What the
app owes"). Re-measure with `sudo RUNTIMES=ply PHASES=churn bench/run.sh`.

## Rolling restart — closed (runs `210430Z`, `211141Z`, churn phase only)

| step | roll errors / 39 M requests |
|---|---:|
| relay, signal-then-remove (morning) | 131 |
| kernel path, remove-then-signal + 1 s drain, app `Shutdown` | 128 |
| + instance joins the pool only once its port accepts | 57 |
| + app drains by `Connection: close` and waits for open connections before `Shutdown` | **0** |

The two halves were one race. Go's `SetKeepAlivesEnabled(false)` and
`Shutdown` both close *idle* connections, and under saturating load every
connection is idle for the instant between a response and the client's next
request already on the wire — one lost request per connection per roll
step, seen by the client as "connection closed" or, when it had just
reconnected, as "connection error". The runtime's share (routing to an
instance before it listened, and signalling before leaving the pool) is
fixed in ply; the app's share is documented in `docs/deploy.md` ("What the
app owes") with the bench API as the reference implementation.

with zero runtime CPU on the kernel path, egress costs nothing on top,
nothing drifts over ten minutes, the runtime is 28 MB against Docker's
150–185, and a rolling restart under load loses nothing when the app drains
properly. Open: P4 (bench debts).
